做动态分析的时候，检测方通常在找 frida-server 的几个典型特征。原生 frida-server 的默认端口是 27042，进程名带 `frida`，文件名是 `frida-server`，线程里能看到 `gum-js-loop`。

加固版把这些**运行时表面特征**全部消除了。但我要说清楚：**这不是 undetectable**，只是把门槛从"扫个端口就能发现"提高到"需要看段名、看内存布局"。

## 可以伪装的部分

| 特征 | 原版 | 加固版 |
|---|---|---|
| 默认端口 | 27042 | 随机高位端口，每次启动变化 |
| 进程名 | `frida-server` | 伪装成系统进程名 |
| 文件路径 | `/data/local/tmp/frida-server` | 随机路径，删除即自毁 |
| 线程名 | `gum-js-loop` 等 | 全部抹除 |
| 文件描述符 | 大量 `anon_inode` | 收敛数量 |

实测下来，用 `ss -lnt` 扫端口、用 `ps -ef` 查进程名、用 `/proc/*/maps` 查映射这三类常见的检测手段，都拿不到稳定信号。

## 抹不掉的部分

这才是重点。下面这些是**深度特征**，做不到根除：

### 1. Agent 段本身

Frida 的 JS 运行时（Gum）在内存里会留下特定的内存布局和可执行页模式。不管进程名、端口怎么改，这段内存还是在。检测方只要扫可执行内存段的特征模式，仍然能命中。

### 2. Java 层的 `System.loadLibrary`

注入点如果走 `System.loadLibrary()`，artmethod 的 native 库映射记录会留下来。用 `ArtMethod` 遍历可以发现加载了非标准 so。

### 3. 线程栈上的 JS 引擎状态

即使线程名抹掉，线程栈里的 V8/Gum 执行上下文还在。`/proc/<pid>/task/*/stat` 的状态字段、栈扫描能看出"这个线程在跑解释器"。

### 4. 时序特征

注入本身有耗时特征（attach 过程、脚本加载），在时间线上会留下不自然的间隔。高频采样的行为检测能看到。

### 5. 内核侧可见性

`/proc/<pid>/maps` 里匿名可执行段的数量、`/proc/<pid>/mem` 的可读性、`ptrace` 的使用痕迹——这些在内核层面是无法从用户态伪装的。

## 我的结论

正确的表述是：**加固版把"特征检测"的成本抬高了一个数量级，但没有消除"行为检测"的可能性。**

所以实际对抗中，加固版的价值在于：

- 对付**通用扫描器**（批量扫端口、扫文件名、扫特征字符串）——完全够用
- 对付**有明确检测规则的对抗方**——需要对方有针对性地写规则，不是开箱即用的
- 对付**内核态/root 级检测框架**——基本无效

不夸大，是这类工具能长期用下去的前提。如果吹成"完全不可检测"，早晚被现实打脸，反而会误导使用者做错误的预期管理。

## 一点工程经验

对抗测试最好在自己的靶机上做。我见过太多"在污染过的现成靶场里测出来 undetectable"的结论——环境不干净，别的 agent 也在跑，检测信号混在一起，结论不可信。

干净基线 + 可回滚快照 + 行为判定，这三件事做到了，结论才有分量。
